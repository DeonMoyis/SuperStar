## 1. 先建立一个整体印象

### 1.1 它到底在干什么

一句话：**模拟一个人在网页上学习的行为，并且让这个行为在时间维度上看起来足够真实。**

「足够真实」是关键词。超星（学习通）不只看你点了什么，还看：

- 你花的时间对不对（视频 60 分钟，你 5 分钟刷完 → 异常）；
- 你提交的频率对不对（一秒交 5 份测验 → 异常）；
- 你的请求参数对不对（`enc` 签名错 → 直接 403）。

所以这个项目的复杂度不在「抓页面」，而在「节奏控制」和「容错」。

### 1.2 分层结构

```
┌─────────────────────────────────────────────────────────┐
│  main.py                                                 │
│  参数解析 · 配置装配 · 课程循环 · 任务调度 · 生命周期收尾   │
└───────────────┬─────────────────────────────┬────────────┘
                │                             │
     ┌──────────▼──────────┐      ┌───────────▼───────────┐
     │ 章节任务点链路        │      │ 作业/考试链路          │
     │ process_course        │      │ AutoAnswer            │
     │  └ JobProcessor       │      │  └ AnswerEngine       │
     │     └ process_job     │      │     └ Tiku / AISolver │
     └──────────┬───────────┘      └───────────┬───────────┘
                │                              │
     ┌──────────▼──────────────────────────────▼───────────┐
     │  api/base.py  Chaoxing                                │
     │  登录 · 课程/章节/任务点 · 视频上报 · 文档 · 测验        │
     └──────────┬───────────────────────────────────────────┘
                │
     ┌──────────▼───────────────────────────────────────────┐
     │ 基础设施层                                             │
     │ SessionManager · RateLimiter · FontDecoder            │
     │ PlaybackGate/AnswerGate · RuntimeBudget · Notification │
     └───────────────────────────────────────────────────────┘
```

### 1.3 模块职责表

| 文件 | 职责 | 关键类/函数 |
| --- | --- | --- |
| `main.py` | 入口、参数、调度、课程循环 | `main()` `JobProcessor` `process_course()` `process_chapter()` |
| `api/base.py` | 所有与超星的 HTTP 交互 | `Chaoxing` `SessionManager` `RateLimiter` `StudyResult` |
| `api/decode.py` | HTML → 结构化数据 | `decode_course_point()` `decode_course_card()` `decode_questions_info()` |
| `api/font_decoder.py` | 字体反混淆 | `FontDecoder.decode()` |
| `api/cxsecret_font.py` | 字体映射表生成 | `font2map()` `decrypt()` |
| `api/answer.py` | 题库抽象与实现 | `Tiku` `TikuYanxi` / `TikuGo` / `TikuLike` / `DeepSeek` … |
| `api/answer_engine.py` | 题目 → 答案 → 表单 | `AnswerEngine` `build_submit_payload()` |
| `api/ai_solver.py` | DeepSeek 调用与治理 | `AISolver` `AICache` `normalize_ai_config()` |
| `api/auto_answer.py` | 作业/考试链路 | `AutoAnswer` `decode_task_list()` |
| `api/playback.py` | 串行闸门 | `SerialGate` `playback_gate` `answer_gate` |
| `api/runtime_budget.py` | 时间盒 | `RuntimeBudget` `runtime_budget` |
| `api/notification.py` | 结果推送 | `Notification` |
| `api/live.py` / `live_process.py` | 直播任务 | `Live` `LiveProcessor` |

设计原则只有两条：

1. **网络交互全在 `base.py`**，其他模块只处理数据。这样接口变了只改一个地方。
2. **节奏控制做成独立的全局对象**（闸门、时间盒），业务代码只管 `with gate.hold()` 和 `if budget.should_stop()`，不关心实现。

## 2. 一次运行的完整生命周期

### 2.1 启动阶段

`main()` 的顺序是有讲究的：

```python
common_config, tiku_config, notification_config = init_config()   # ① 配置
configure_console_logger(...)                                     # ② 日志
common_config["speed"] = normalize_speed(...)                     # ③ 倍速强制归一
runtime_budget.configure(common_config.get("max_runtime_minutes"))# ④ 时间盒启动
ai_solver = configure_default_solver(common_config.get("ai"))     # ⑤ AI 初始化
chaoxing = init_chaoxing(...)                                     # ⑥ 题库 + 会话
chaoxing.login(...)                                               # ⑦ 登录
```

几个细节：

- **③ 在 ④ 之前**：倍速归一必须早于任何播放，否则 `JobProcessor` 可能拿到未归一的值。同时 `JobProcessor.__init__` 里还会再 `normalize_speed` 一次做双保险。
- **④ 在 ⑥ 之前**：`runtime_budget.configure()` 会重置计时起点，必须在真正开始干活之前调用。如果放在登录之后，登录耗时就不计入预算了（其实更合理，但会让人对不上账，所以选了「从启动算起」）。
- **⑤ 的连通性检查是软失败**：Key 无效时只把 `mode` 改成 `off` 然后继续跑，不 `raise`。因为「Key 填错」不应该让整个刷课流程崩掉。

```python
if ai_config.enabled and ai_config.check_connection:
    ok, message = ai_solver.check_connection()
    if not ok:
        logger.error("[AI] 本次不使用 AI 作答, 题目将由题库/随机答案兜底")
        ai_config.mode = "off"
        ai_solver.config.mode = "off"   # 注意要改两处
```

`ai_config` 是局部副本，`ai_solver.config` 是真正被使用的对象，两个都要改。

### 2.2 主循环

```python
answer_order = common_config.get("answer_order", "after")    # after / before / both

if answer_only:
    for course in course_task:
        answer_course(course, "唯一一轮")
else:
    for course in course_task:
        if runtime_budget.should_stop(): break          # ← 课程之间检查
        if answer_order in ("before", "both"):
            answer_course(course, "刷课前")
        process_course(chaoxing, course, common_config)
        if answer_order in ("after", "both"):
            answer_course(course, "刷课后")             # ← 默认刷完这门课再做
```

**默认「先刷课、后做题」，而且是以课程为单位闭环**：第 1 门课的 `学内容 → 本节测验 → 作业/考试` 全部走完，才进第 2 门课。

为什么不是"所有课刷完再统一做题"（老行为）：视频按 1 倍速串行播，一次运行大概率刷不完，如果作业排在所有课程之后，它会被永远饿死 —— 很多课是「每小节一个视频 + 一份作业」，视频刷到一半收工，作业却一份没做。改成按课程闭环后，即使中途撞上 `max_runtime`，前面几门课也是完整交付的。

为什么默认不是「先做题」：作业和考试基本都是**学完前几节才解锁**的，抢在前面做只会撞上"未开始/未解锁"，白跑一趟。想先做题用 `before`，想前后各扫一遍用 `both`（幂等，已完成的不再扫到）。

这个顺序还有一个附带性质：**考试和视频永远不会同时在跑**，所以作业/考试链路不需要和播放闸门抢锁。

### 2.3 收尾

```python
finally:
    release_default_solver()   # 把 AI 答案缓存落盘
```

`release_default_solver()` 会 `flush()` 缓存并解除全局单例。放在 `finally` 里是因为：即使中途抛异常，已经花钱问到的答案也应该存下来，下次不用重复付费。

## 3. 与超星通信的底层细节

这一章是理解整个项目的关键。搞不清这些，`base.py` 里的很多「多余代码」看起来都像乱写。

### 3.1 登录：AES + 一个会话

```python
_url = "https://passport2.chaoxing.com/fanyalogin"
_data = {
    "fid": "-1",
    "uname": self.cipher.encrypt(self.account.username),
    "password": self.cipher.encrypt(self.account.password),
    ...
}
```

账号密码不是明文 POST，而是经过 `AESCipher`（在 `api/cipher.py`）加密。密钥硬编码在源码里（前端 JS 里能扒出来，不是秘密）。加密后的字符串形如 `xxxx==`，服务端解出来再验证。

登录成功后：

```python
save_cookies(_session)          # 落盘到 cookies.txt，供 --use-cookies 复用
SessionManager.update_cookies() # 用这份 cookie 重建全局 session
```

**为什么要 `SessionManager` 这个看起来多余的单例？**

因为超星的接口散落在 `mooc1.chaoxing.com`、`mooc2-ans.chaoxing.com`、`mooc1-api.chaoxing.com` 等一堆域名下，而它们共享同一批 cookie。用同一个 `requests.Session` 才能自动带上所有 cookie，并且复用连接池。

```python
class SessionManager:
    def __new__(cls, *args, **kwargs):   # 单例
```

`--use-cookies` 模式不是「相信 cookie 存在就行」，而是真的验证一次：

```python
def _validate_cookie_session(self):
    resp = test_session.post("https://mooc2-ans.chaoxing.com/mooc2-ans/visit/courselistdata", ...)
    if "passport2.chaoxing.com" in resp.text:   # 被踢回登录页
        return False
```

判断依据很朴素：**如果你被重定向回登录页，说明 cookie 失效了**。这比检查某个 cookie 键是否存在靠谱得多（过期了键还在）。

### 3.2 限流器：为什么要两种速率

```python
self.rate_limiter = RateLimiter(0.5)       # 普通接口, 500ms 一次
self.video_log_limiter = RateLimiter(2)    # 进度上报, 2s 一次
```

进度上报用的是**单独**的、慢得多的限流器。原因是这个接口最敏感：

- 调太快 → 直接返回 403，或者弹图形验证码；
- 403 之后如果不退避继续打，会被拉黑更久。

其他接口（拉列表、取章节）宽松很多，500ms 足够。

实现方式很朴素——记录上次调用时间，不够就 `time.sleep()`：

```python
def limit_rate(self, random_time=False, random_min=0.0, random_max=1.0):
```

`random_time=True` 时额外加一个随机抖动。这不是为了好看：**固定间隔的请求序列在流量分析下一眼就是脚本**，加抖动能让时间分布接近真人。

### 3.3 课程 → 章节 → 任务点：三层解析

| 层级 | 接口 | 解析函数 | 产出 |
| --- | --- | --- | --- |
| 课程 | `mooc2-ans/visit/courselistdata` | `decode_course_list()` | `courseId` `clazzId` `cpi` `title` |
| 章节 | `mooc2-ans/mycourse/studentcourse` | `decode_course_point()` | `points[]`，每项含 `knowledgeid` `title` |
| 任务点 | `mooc-ans/knowledge/cards` | `decode_course_card()` | `jobs[]` + `job_info` |

任务点解析是最脏的一层。`decode_course_card()` 返回的卡片里，类型是靠 `card['type']` 和附件字段组合判断的：

```python
_process_video_task()     # 视频
_process_document_task()  # 文档
_process_work_task()      # 章节测验 (workid)
_process_read_task()      # 阅读
_process_live_task()      # 直播
```

每种任务点最后都会被标准化成同一个结构，供 `process_job()` 分发：

```python
{
    "type": "video" | "document" | "workid" | "read" | "live",
    "jobid": "...",
    "objectid": "...",
    "otherinfo": "...",       # 视频上报时要原样带回
    "name": "第一章 视频",
    ...
}
```

> **`otherinfo` 是什么？** 一串 URL 编码的参数，含 `_rt`、节点信息等。进度上报时**必须原样回传**，否则服务端认不出这个任务点。不要试图解析或重写它。

### 3.4 视频进度上报：`enc` 签名

这是整个项目最容易踩坑的地方。上报地址：

```
GET https://mooc1.chaoxing.com/mooc-ans/multimedia/log/a/{cpi}/{dtoken}
```

参数里的 `enc` 是一个 MD5 签名：

```python
def get_enc(self, clazzId, jobid, objectId, playingTime, duration, userid):
    return md5(
        f"[{clazzId}][{userid}][{jobid}][{objectId}]"
        f"[{playingTime * 1000}][d_yHJ!$pdA~5]"
        f"[{duration * 1000}][0_{duration}]"
        .encode()
    ).hexdigest()
```

拆开看就是：

| 段 | 含义 |
| --- | --- |
| `[clazzId]` | 班级 ID |
| `[userid]` | 你的 UID（从 cookie `_uid` 取） |
| `[jobid]` | 任务点 ID |
| `[objectId]` | 媒体对象 ID |
| `[playingTime * 1000]` | **已播时长，毫秒** |
| `[d_yHJ!$pdA~5]` | 固定盐值（前端 JS 里的硬编码常量） |
| `[duration * 1000]` | **总时长，毫秒** |
| `[0_{duration}]` | clipTime，秒 |

两个容易致命的点：

1. **单位是毫秒**。传秒进去，签名必然错，服务端返回 403。
2. **`playingTime` 必须单调递增**。往回跳会被判为拖动（`isdrag`），可能不计入时长。

### 3.5 `rt` 与 `isdrag`

`rt` 是个奇怪的小参数，取值 `0.9` 或 `1`，影响能否被判定为「正常播放」。它藏在 `otherinfo` 里：

```python
rt_search = re.search(r"-rt_([1d])", _job['otherinfo'])
rt = "0.9" if rt_char == "d" else "1"
```

如果 `otherinfo` 里找不到，就两个都试一遍（0.9 → 1），哪个返回 200 用哪个。这是实测出来的经验值，没有文档。

`isdrag` 是「是否拖动」标记：

| 值 | 含义 | 用在哪 |
| --- | --- | --- |
| `3` | 正常播放 | 循环上报 |
| `4` | 拖动定位 | 开播前的「秒完成」探测 |

开播时先发一次 `isdrag=4` + `playingTime=duration` 的请求，看服务端是否直接返回 `isPassed=true`：

```python
passed, state = self.video_progress_log(..., duration, duration, ..., _isdrag=4)
if passed:
    logger.info("任务瞬间完成: {}", _job['name'])
    return StudyResult.SUCCESS
```

这处理的是**已经看过的视频**。既然服务端认为看完了，就没必要再播一遍。注意这不算作弊——前提是服务端自己认了。

另外还有三个可选参数，只有在页面给了才传：

```python
if face_capture_enc: params["videoFaceCaptureEnc"] = face_capture_enc   # 人脸识别任务
if att_duration:     params["attDuration"] = att_duration               # 附件时长
if att_duration_enc: params["attDurationEnc"] = att_duration_enc
```

`videoFaceCaptureEnc` 是开启了人脸识别的课程才有的。传了也不代表人脸真的通过了——那部分本项目不做处理。

### 3.6 403 之后会发生什么

403 是超星最常见的反制手段。处理策略是**先救、救不了就跳过，绝不硬刚**：

```python
if state == 403:
    if forbidden_retry >= max_forbidden_retry:      # 最多救 2 次
        return StudyResult.FORBIDDEN
    forbidden_retry += 1
    time.sleep(random.uniform(2, 4))                # 先退避
    refreshed_meta = self._recover_after_forbidden(_session, _job, _type)
```

`_recover_after_forbidden()` 会重新请求 `/ananas/status`，拿到新的 `dtoken`、`duration`、`playTime`。`dtoken` 是会过期的，403 很多时候就是它过期了。

**这里有一个曾经的真实 bug**，值得单独说：

```python
# 刷新后的 playTime 可能是毫秒, 直接当秒用会被 min(duration, ...) 截断 → 秒看完
play_time = normalize_play_time(refreshed_meta.get("playTime"), duration)
```

`/ananas/status` 返回的 `playTime` 单位不固定（秒或毫秒），而旧代码直接当秒用。一个「120000」进了 `min(720, 120000)`，立刻被判定为播完，视频几秒钟就结束了。`normalize_play_time()` 做自适应换算：

```python
def normalize_play_time(value, duration):
    if value > duration * 10:      # 明显是毫秒
        value = value / 1000
```

判断依据是「**如果比总时长还大一个数量级，那一定是毫秒**」。简单但够用。

### 3.7 字体反混淆

某些课程的题目、选项文字是用自定义字体渲染的：文字在 HTML 里是乱码，靠 `@font-face` 内嵌的 TTF 还原。

流程：

```
HTML 里的 <style id="cxSecretStyle">
   └─ base64 TTF
        └─ font2map()  →  {glyph_id: 真实字符}
             └─ decrypt()  →  把乱码文本逐字替换回正常文字
```

`decode_questions_info()` 的入口判断很直接：

```python
has_font_encryption = bool(soup.find("style", id="cxSecretStyle"))
if has_font_encryption:
    font_decoder = FontDecoder(html_content)
```

关键点：**每份页面都可能用不同的字体**，所以不能缓存解码器，必须每次新建。`FontDecoder` 的 `__init_font_map()` 失败时只打警告不抛异常——没有加密的页面本来就不该失败，有加密但解不出来则退化为原始文本，让后面「AI 猜答案」还有机会。

### 3.8 章节测验的提交语义：`pyFlag`

`pyFlag` 是「保存 vs 提交」的开关：

| 值 | 语义 |
| --- | --- |
| `""` | 正式提交，计入成绩 |
| `"1"` | 只保存草稿，可以继续改 |

所以覆盖率不达标时：

```python
questions["pyFlag"] = "1"      # 只保存
```

谁来决定提交还是保存？**`[answer] submit_policy`**，作业、考试、章节测验共用同一份策略：

```python
submit = self._should_submit(cover_rate)   # always / never / auto(>= min_cover_rate)
questions["pyFlag"] = "" if submit else "1"
```

早期版本把章节测验的提交绑定在 `[tiku] submit` 上，导致「只用大模型、没配题库」的人即使答对了也永远只保存草稿，任务点始终不通过。现在统一走 `[answer]`，`[tiku] submit` 仅为兼容旧配置保留。

同时 `build_submit_payload()` 会把**随机兜底**的答案清空，避免把乱填的内容写进草稿：

```python
if not submit_mode and item.source not in {"tiku", "ai"}:
    answer_value = ""
```

题库命中或 AI 作答的答案会保留——它们有参考价值，你手动检查时能省一半力气。

## 4. 播放节奏控制

### 4.1 问题本质

上报的 `playingTime` 是「视频内时间」，而服务端校验时对比的是「两次上报之间的真实时间差」。理想情况：

```
ΔplayingTime ≈ Δ真实时间 × 播放倍速
```

只要这个比值明显大于 1，就有风险。所以：

| 做法 | 对 `ΔplayingTime / Δ真实时间` 的影响 |
| --- | --- |
| 2 倍速 | 直接 = 2，必然异常 |
| 4 个视频并发 | 每个视频自身是 1，但**整门课的完成速度**是 4 倍 |
| 1 倍速 + 串行 | = 1，和真人一致 |

第二种最阴险：单看每个视频都正常，但一门 40 小时的课 10 小时就刷完了。用户看到的现象是「明明是 1 倍速，为什么这么快」。

### 4.2 `SerialGate` 的实现

核心就是一个信号量：

```python
class SerialGate:
    def __init__(self, resource_name, unit_name, busy_text, stat_label):
        self._sem = threading.Semaphore(1)
```

`hold()` 是一个上下文管理器，`yield` 的是**布尔值**（是否抢到），而不是无条件阻塞：

```python
@contextmanager
def hold(self, name="", should_stop=None):
    while not self._sem.acquire(timeout=1):
        if should_stop is not None and should_stop():
            yield False
            return
        ...
    try:
        yield True
    finally:
        self._sem.release()
```

**为什么用 `timeout=1` 轮询而不是直接 `acquire()` 阻塞？**

因为要响应 `should_stop`。如果直接阻塞，一个排队中的视频可能在时长上限到了之后仍然傻等半小时。用 1 秒轮询，最长 1 秒内就能放弃。

### 4.3 一个必须做对的细节：`last_iter` 的位置

```python
with playback_gate.hold(_job['name'], should_stop=runtime_budget.should_stop) as acquired:
    last_iter = time.time()          # ← 必须在拿到播放位之后
    play_started_at = last_iter
```

如果 `last_iter` 在函数开头初始化，排队等待的 20 分钟会被这行算进去：

```python
dt = (time.time() - last_iter) * _speed      # dt = 1200 秒!
play_time = min(duration, play_time + dt)    # 直接跳到片尾
```

**这才是「秒看完」最隐蔽的来源**——不是倍速，不是服务端放行，是自己把排队时间当成了播放时间。

### 4.4 两个闸门，为什么不能合并

```python
playback_gate = PlaybackGate()   # 管视频播放位
answer_gate = AnswerGate()       # 管测验作答位
```

看起来可以共用一个信号量（反正都要串行），但实际上不行：

- `playback_gate` 会被占用**几十分钟**（一个视频的时长）；
- `answer_gate` 只占几秒到几十秒。

合并的后果是：一个测验排在视频后面，要等几十分钟才能开始答。而它们本来就是不同性质的资源，没必要互相排队。

两者的行为完全一致（都是 `SerialGate` 的实例），只是日志措辞不同——分开是为了让人能读懂日志。

### 4.5 章节内为什么改成串行

早期版本 `process_chapter()` 里是：

```python
with ThreadPoolExecutor(max_workers=5) as executor:      # 旧实现
    for result in executor.map(lambda job: process_job(...), jobs):
```

一个章节的所有任务点一起丢进 5 线程池，看起来很高效，实际上有两个真实问题：

**问题 1：先做题、后看视频。** 视频要先排队拿播放位（`playback_gate`），而章节测验拿的是另一个闸门（`answer_gate`），两者不互斥。于是测验常常在视频还在排队时就先跑完了 —— 表现为「这一节的视频还没看，测验已经交了」。而超星的章节测验普遍要求**先学完本节内容**才允许作答，抢在前面提交容易判未完成。

**问题 2：章节内多个视频的播放顺序是乱的。** `SerialGate` 底层是 `threading.Semaphore`，不保证公平，5 个线程谁先抢到谁先播。第 2 个视频排到第 1 个前面，进度校验和"未完待续"的情况下都会变得难以解释。

现在的实现：

```python
content_jobs = [j for j in jobs if j.get("type") != "workid"]   # 视频/文档/阅读/直播
quiz_jobs    = [j for j in jobs if j.get("type") == "workid"]   # 本节测验
ordered_jobs = content_jobs + quiz_jobs                          # 先内容, 后测验

for job in ordered_jobs:
    if runtime_budget.should_stop():
        job_results.append(StudyResult.SKIPPED)
        continue
    job_results.append(process_job(...))
```

**并发在这里没有收益**：1 倍速已经把视频播放压成严格的串行，5 个线程只是排队。串行换来的确定性（顺序正确、不和风控赛跑、日志可读）明显更值。真正的并行度由 `jobs`（章节并发，默认 1）控制。

`answer_gate` 仍然保留：当 `jobs > 1` 时，不同章节的测验可能同时要作答，闸门保证同一时刻仍然只有一份在提交。

原始的 `study_work` 本体原封不动改名成 `_study_work_locked`，外面套一层拿闸门的壳——那个方法有 300 多行，整体重写风险远大于套壳。

### 4.6 视频刷不过去：三种成因的区分

「`playTime` 推到 `duration`，服务端 `isPassed` 仍然是 `false`」是这套代码里最容易被误判的问题。它至少有三种完全不同的成因，处理方式也完全不同：

| 成因 | 证据 | 能不能自动解决 |
| --- | --- | --- |
| 视频内嵌题（弹窗题） | 卡片 / initdata 里能解析出题目 | 可以，播到弹题时间自动作答并提交 |
| 人脸采集 | `videoFaceCaptureEnc` 非空 | 不行，必须真人过人脸 |
| 服务端状态延迟 / 风控 | 两者都没有 | 只能重试或降频 |

只看 `isPassed` 是分不出来的，所以 `api/video_quiz.py` 提供两个能力：

**`find_inline_questions(raw_card)`** —— 结构化扫描。不写死路径，因为它跟着课程版本变；判定条件是「同时具备题干和选项或题型」，避免把 `name`、`title` 这类普通字段误判成题目：

```python
_TITLE_KEYS  = ("title", "question", "content", "stem", "qtitle", "name")
_OPTION_KEYS = ("options", "option", "choices", "optionList")
_TYPE_KEYS   = ("type", "questionType", "qtype", "question_type")

def _looks_like_question(node):
    if not _first_str(node, _TITLE_KEYS):
        return False
    has_options = any(node.get(k) for k in _OPTION_KEYS)
    return (has_options and _normalize_type(...)) or _normalize_type(...) == "judgement"
```

**`summarize_video_card(raw_card)`** —— 把三个证据汇总成一句话，直接写进日志：

```python
if questions:            reason = "卡片里带弹窗题"
elif face_enc:           reason = "该视频开启人脸采集, 纯 HTTP 无法完成"
else:                    reason = "卡片里没发现弹窗题, 也不像人脸采集"
```

题目数据原先是被丢掉的：`_process_video_task()` 只挑 7 个字段（`jobid`/`objectid`/`otherInfo`/`playTime`/`rt`/`attDuration*`/`videoFaceCaptureEnc`），现在多带一个 `raw_card`，否则解析器根本看不到题目。

作答入口有两条，**都不靠猜接口**：

1. **开播前拉题目**（主路径）：`GET /mooc-ans/richvideo/initdatawithviewerV2?start=undefined&mid=<mid>`。
   响应里每道题都带 `startTime`（第几秒弹）、`validationUrl`（提交地址）、`resourceId` 和选项。
   播放循环每推进一次就调 `_submit_due_inline_quizzes()`，进度越过 `startTime` 就作答并提交：

   ```python
   GET https://mooc1.chaoxing.com{validationUrl}?resourceid=<resourceId>&answer=<选项 name>
   ```

   注意提交的是选项的 `name` 而不是字母 A/B/C —— 有的课程下发的 name 是选项 id，
   所以 `option_name_for_letter()` 按顺序取，别直接把字母塞进去。

2. **进度响应兜底**：`_capture_inline_questions()` 挂在 `video_progress_log()` 解析响应的地方，
   响应里带题且带 `validationUrl` 时顺手提交；只有题目没有地址时，就只作答并留证据。

同一道题按 `id` 或题干去重（`_inline_seen`），提交过就置 `_done`，绝不会重复提交。
题目会先被归一成章节测验那套结构（`A.选项内容\nB.选项内容`），再交给 `AnswerEngine`，
所以题库、大模型、图片题标记这些能力全都能复用。

收尾时 `chaoxing.inline_quiz_stat` 会汇总「共几道 / 作答几道 / 提交成功几道 / 失败几道」，
和「需人工处理的视频任务点」一起进日志与通知。

诊断数据落盘由 `--video-debug` 控制，写到 `video_debug/`：

```python
configure_video_debug("video_debug")   # main.py, 仅在该开关打开时生效
save_video_debug(f"stuck_{jobid}.json", diag)   # 卡片 + status + 最近响应
```

没开开关时 `save_video_debug()` 是一个直接返回的空操作，不影响正常流程。

最后，被跳过的任务点会进入 `chaoxing.stuck_points`，在程序收尾时汇总打印，并拼进通知消息——避免「跑完看起来全绿，其实漏了几个」。

### 4.7 任务点没完成：从头重播一遍

超星的任务点校验是「连续观看」语义：上一次运行留下的 `playTime` 可能让服务端认为
「进度不对劲」，于是进度推到片尾也不给 `isPassed`。旧实现到这一步就 `SKIPPED`，
任务点一直空着，下次运行还是同样的死结。

现在把 `study_video()` 拆成两层：

```python
def study_video(...):
    result, stuck = self._study_video_once(..., restart_from_zero=False)
    if result == StudyResult.SUCCESS or not stuck:
        return result
    # 卡住 -> 忽略已记录进度, 从 0 秒真播一遍
    return self._study_video_once(..., restart_from_zero=True)[0]
```

两个关键点：

- **只有 `stuck=True` 才重播**。403、到达运行时长上限、服务端状态异常都不重播 ——
  它们不是「进度不对」，重播只会白烧时间；
- **重播只做一次**。第二次还不行就放弃并记进 `stuck_points`，否则就是换了个形式的死循环。

`restart_from_zero=True` 时还会跳过开播前的 `_isdrag=4` 冲刺探测 —— 那一步是「上报一个
已到片尾的进度碰运气」，在重播场景下等于自欺欺人，必须真播。

## 5. 时间盒：可控地中断

### 5.1 为什么需要

两个现实约束：

1. 有些学校要求「不能一次性刷完」，要分多次；
2. GitHub Actions 单 job 上限 6 小时，跑不完就是硬中断。

硬中断的后果是**任务做一半**：视频播到 80% 被掐，可能留半截进度甚至触发回滚。

所以需要一个「**到点不接新活，把手上的干完再走**」的机制。

### 5.2 `RuntimeBudget` 的 API

| 成员 | 作用 |
| --- | --- |
| `configure(minutes)` | 设置上限并**重置计时起点** |
| `remaining` | 剩余秒数，未限制时返回 `None` |
| `expired` | 是否已到点 |
| `should_stop()` | 是否该停，**首次命中时打一条日志** |
| `summary()` | 结束时的一句话总结 |

`should_stop()` 里的 `_notified` 标志是必要的：

```python
def should_stop(self):
    if not self.expired:
        return False
    with self._lock:
        if not self._notified:
            self._notified = True
            logger.warning(f"已达到单次运行时长上限 ...")
    return True
```

因为这个方法会被**几十个线程高频调用**（每个任务点、每次排队轮询）。不控制的话日志会被刷屏几千行。

`configure()` 的容错也很宽松：`None`、`""`、`0`、`"0.0"`、负数、非数字，全部当作「不限制」，只对真正的异常值打一条警告。

### 5.3 最难的地方：让 `task_queue.join()` 返回

`JobProcessor.run()` 的结构是：

```python
for task in self.tasks:
    self.task_queue.put(task)
# ... 启动 worker ...
self.task_queue.join()      # ← 阻塞直到队列清空且全部 task_done
```

`join()` 的语义是「所有任务都 `task_done()` 了才返回」。如果到点时队列里还剩 20 个任务没处理，`join()` 会**永远等下去**——worker 都已经因为 `should_stop` 返回了，没人再去 `task_done()`。

这就是 `_abort_pending()` 的存在意义：

```python
def _abort_pending(self):
    while True:
        try:
            task = self.task_queue.get_nowait()
        except Empty:
            break
        if self._is_stop_task(task):
            self.task_queue.task_done()
            continue
        task.result = ChapterResult.SKIPPED
        self.skipped_tasks.append(task)
        self.task_queue.task_done()      # ← 关键
```

配套一个监控线程：

```python
def _budget_monitor(self):
    while not self.budget_stop.wait(2):      # 每 2 秒看一次
        if runtime_budget.should_stop():
            self._abort_pending()
```

还有一处容易漏：`worker_thread` 从队列取到任务之后、真正执行之前，也要再查一次：

```python
if runtime_budget.should_stop():
    task.result = ChapterResult.SKIPPED
    self.task_queue.task_done()
    return
```

否则会出现「drain 之后又有 worker 从队列取到活」的竞态——虽然 `_abort_pending` 已经把队列清空，但取任务和执行之间有时间窗口。

### 5.4 为什么 `SKIPPED` 不是失败

`StudyResult` 里：

```python
def is_failure(self):
    # SKIPPED 属于「这次没做」而不是「做失败了」, 不能触发重试
    return self not in (StudyResult.SUCCESS, StudyResult.SKIPPED)
```

如果 `SKIPPED` 算失败，重试线程会疯狂重排这些任务，最后 `max_tries=5` 全部耗尽，日志里一堆假错误。而且下次运行本来就会重新扫描，重试毫无意义。

### 5.5 软上限

时间盒只在**任务之间**检查，不打断正在执行的任务。所以：

```
实际结束时间 ≈ 上限 + 最后一个任务的剩余时长
```

这是刻意的：掐断视频会留半截进度、可能回滚，比多跑 20 分钟糟糕得多。

## 6. 任务调度器

### 6.1 三条队列

```python
self.task_queue  = PriorityQueue()   # 待处理章节
self.retry_queue = PriorityQueue()   # 待重试章节
self.wait_queue  = PriorityQueue()   # 预留: 章节未开放时挂起(当前未启用)
```

`PriorityQueue` 里放的是 `ChapterTask`：

```python
@dataclass(order=True)
class ChapterTask:
    index: int
    point: dict[str, Any] = field(compare=False)
    result: ChapterResult = field(default=ChapterResult.PENDING, compare=False)
    tries: int = field(default=0, compare=False)
```

`order=True` + `compare=False` 是这里的要点：**只有 `index` 参与比较**，其余字段不影响排序。如果 `point`（一个 dict）参与比较，`PriorityQueue` 在元组比较时会直接抛 `TypeError`。

按 index 排序保证**章节顺序执行**（虽然视频已经串行了，但顺序执行让日志更好读，也更像真人在按顺序学）。

### 6.2 停止哨兵

worker 是靠哨兵任务退出的：

```python
STOP_POINT = {"__stop__": True}

def _stop_task(self):
    return ChapterTask(index=sys.maxsize, point=self.STOP_POINT)
```

`index=sys.maxsize` 保证它排在所有真实章节之后——否则一个 `PriorityQueue` 里的停止信号可能先于章节被取走，直接导致后面的章节全不处理。

### 6.3 重试与过载保护

```python
self.max_tries = 5
```

失败的任务进 `retry_queue`，重试次数 +1，超过上限就进 `failed_tasks` 并放弃。重试不是立刻的——`retry_thread` 从 `retry_queue` 取到后放回 `task_queue`，等 worker 空闲再处理，天然起到延迟作用。

## 7. 答题体系

### 7.1 三层结构

```
AnswerEngine            ← 编排: 每道题走哪条路
   ├─ Tiku (题库)       ← 查现成答案
   ├─ AISolver          ← 问大模型
   └─ 随机兜底
```

三条答题入口共用这一个引擎：

| 入口 | 触发位置 | 说明 |
| --- | --- | --- |
| 章节测验 | `Chaoxing.study_work()` | 章节任务点里的 `workid`，即「每小节那份作业」 |
| 作业 | `AutoAnswer.run_course()` | 课程「作业」列表 |
| 考试 | `AutoAnswer.run_course()` | 课程「考试」列表，可 `--no-exam` 关闭 |

`study_work()` 的门槛是 `_answer_available()`——**题库或大模型有一个能用就放行**：

```python
def _answer_available(self) -> bool:
    engine = getattr(self, "answer_engine", None)
    return bool(engine and engine.has_answer_source())
```

早期版本这里写的是 `if self.tiku.DISABLE: return SUCCESS`，只看题库。对「只填了 DeepSeek Key、没配 `[tiku]`」的用户来说，章节测验会被逐份静默跳过，日志里只有一句 `未找到tiku配置`，看起来像「作业莫名其妙没做」。

### 7.2 题库抽象

`Tiku` 基类定义接口，所有 provider 继承它：

```python
class Tiku:
    DISABLE = False     # 停用标志
    SUBMIT = False      # 是否自动提交
    COVER_RATE = 0.8    # 覆盖率阈值

    def init_tiku(self):        # 读配置 + 子类初始化
    def _init_tiku(self):       # 子类实现
    def query(self, q_info):    # 子类实现: 返回答案字符串
    def judgement_select(self, answer):  # 判断题归一化
```

`q_info` 的结构：

```python
{"id": "9001", "title": "1+1=?", "options": "A.1\nB.2\nC.3", "type": "single"}
```

`query()` 返回的是**原始答案文本**（可能是 `"B"`、`"2,4"`、`"正确"`），由引擎负责转成选项字母。

多题库回退靠 `TikuFallback`——按 `provider` 配置顺序依次问，前一个返回 `None` 才问下一个。

```python
PROVIDER_REGISTRY = {
    'TikuYanxi': TikuYanxi,
    'TikuGo': TikuGo,
    'TikuLike': TikuLike,
    'TikuAdapter': TikuAdapter,
    'AI': AI,
    'SiliconFlow': SiliconFlow,
    'DeepSeek': DeepSeek,
}
```

`DeepSeek` 是个适配器：把 `AISolver` 包装成 `Tiku` 接口，这样章节测验就能复用 `[ai]` 的 Key 和缓存。

### 7.3 答题引擎：逐级降级

```python
def solve_one(self, question):
    # ① 题库 (或 AI, 取决于 ai_mode)
    # ② 匹配: 答案文本 → 选项字母
    # ③ 失败 → 随机兜底
```

匹配是最有技术含量的部分，`_match_answer()` 按题型分派：

**单选题** `_match_single()`：

```
"B"                → "B"        直接是字母
"2"                → "B"        答案文本精确等于某个选项内容
"选项B"            → "B"        去除前后缀
"比萨斜塔"          → "C"        相似度匹配 (difflib, 阈值 0.8)
"2、4"             → ""         多值, 单选无法匹配
```

**多选题** `_match_multiple()`：

```
"AC"               → "AC"       连续字母拆分
"2,4"              → "BD"       按选项内容逐个匹配
"A,C"              → "AC"       混合分隔符
"A、C、D"          → "ACD"
```

匹配结果**排序去重**后返回，因为超星要求字母升序。

相似度兜底用的是 `difflib.SequenceMatcher`：

```python
@classmethod
def _best_option_by_similarity(cls, target, options, threshold=0.8):
```

阈值 0.8 是调出来的：太低会匹配错（"马克思主义" vs "马克思主义基本原理"），太高会匹配不上（题库答案常有细微差异）。

**随机兜底**不是纯随机：

```python
def _random_multiple_count(option_count):
    # 多选随机 2~3 个, 而不是全选或只选一个
```

多选题随机选 2~3 个，因为统计上多选正确答案很少是 1 个或全部。

### 7.4 AI 求解器

#### 为什么重写

早期的 `AI` 题库有三个硬伤：

| 问题 | 后果 |
| --- | --- |
| 提示词把选项字母删掉只给内容 | 模型回内容，程序再猜第几个 → 猜错 |
| 没有 JSON 约束 | 模型带解释、带 markdown，解析失败即丢弃 |
| 没有重试/缓存/并发 | 几十道题串行，慢且贵 |

#### 现在怎么做的

**提示词**（`SYSTEM_PROMPT`）明确要求：

```
1. 只输出一个 JSON 对象，不要输出 markdown 代码块、不要输出任何解释性段落。
2. 先在 analysis 里做推理，再给 answer（analysis 写在 answer 前面）。
3. 单选题：answer 里只放一个选项字母，例如 ["B"]。
4. 多选题：answer 里放所有有依据的选项字母，按字母升序；宁可少选也不要凑数。
5. 判断题：answer 里只放 "正确" 或 "错误"。
```

第 2 条是「伪思维链」：JSON 对象的键是**按顺序生成**的，把 `analysis` 放在 `answer` 前面，
模型必须先写出推理再落答案，比直接要答案的错误率明显低一档。关掉 thinking 时也能起到一部分作用。

第 4 条早期写的是「不确定时也要选出至少两个」，这条是**反效果**的：多选题错一个通常整题判 0，
它等于逼模型在没把握时瞎猜。现在改成「只选有依据的，宁可少选」。

**请求侧**三重约束：

```python
kwargs["response_format"] = {"type": "json_object"}          # 官方 JSON Output
kwargs["temperature"] = 0.2                                   # 低温度, 稳定
if not config.thinking:                                       # 深度思考默认开
    kwargs["extra_body"] = {"thinking": {"type": "disabled"}}  # 只有显式关掉时才发这个字段
```

开思考时 `max_tokens` 会被自动抬到 4096（`THINKING_MIN_TOKENS`）：思考 token 也算在输出配额里，
用默认的 1024 会被思考过程吃光，接口返回空 `content`，重试几次后整道题就丢了。
另外思考模式与 `response_format` 在部分端点不兼容（400），`_request()` 会自动去掉 JSON 约束降级为文本解析。

`max_retries=0` 传给 OpenAI 客户端，重试由自己控制——否则客户端内部重试和外部重试叠加，一次失败会打出多个请求。

**解析**是多层兜底：

```
json.loads(text)
  ├─ 失败 → 去掉 ```json 代码块再试
  ├─ 失败 → 正则截取第一个 { ... }
  └─ 失败 → 纯字母兜底（正则找 [A-Z]）
```

**校验与自动纠错**（这是「完善」的核心）：

```python
problem = self._postprocess(q_info, answer)      # None = 通过, 否则是问题描述
if problem:
    repair_messages = messages + [
        {"role": "assistant", "content": answer.raw or json.dumps(...)},
        {"role": "user", "content": REPAIR_PROMPT.format(problem=problem, letters="A/B/C")},
    ]
    repaired = self._ask(repair_messages, q_info)
```

`_postprocess()` 不只是校验，还会**就地规范化**：

- 选择题：调 `_coerce_letters()` 把内容反查成字母，再检查字母是否都在可选范围内；
- 单选题：必须恰好一个；
- 多选题：至少一个，最后 `sorted(set(...))` 去重排序；
- 判断题：用 `_is_true()` 把「对/√/是/True」统一成 `"正确"`。

`_coerce_letters()` 是关键的一步——模型有时仍然回选项内容（比如 `"2,4"`）而不是字母，它负责反查：

```
"2"        → ["B"]
"2,4"      → ["B", "D"]
"AC"       → ["A", "C"]
"选项B"    → ["B"]
```

`REPAIR_PROMPT` 会把具体问题塞回去，比如：

```
你上一轮的答案是 ["Z"]，但本题只有 A/B/C 三个选项。请重新作答。
```

这比「重新生成」有效得多——模型知道错在哪，通常一次就能改对。纠错后仍不合法则直接放弃这道题的 AI 答案，交给下一级兜底，避免拿一个错误答案去覆盖正确结果。

**缓存**：

```python
def make_key(q_info):
    raw = "|".join([CACHE_VERSION, namespace(模型名), type, 去空白的title, 去空白的options])
    return md5(raw)
```

键包含版本号 + 模型名 + 题型 + 题干 + 选项，任一不同就算不同题。落盘到 `ai_cache.json`，`_dirty >= 10` 时批量写入。

两个「别把错误固化下来」的细节：

- **版本号**：`CACHE_VERSION` 一改（提示词或校验逻辑变了就 +1），旧缓存全部失效。
  否则前一天答错的答案会被永久复用，改提示词也没用；
- **低置信度不缓存**：`confidence < 0.5` 的答案基本等于猜的，不写盘，下次重新问。

**为什么「网页版答得对、程序答错」**——三个差异，按影响排序：

| 差异 | 说明 | 对策 |
| --- | --- | --- |
| 模型档位 | 网页版开「深度思考」= 推理档；程序默认 `thinking=false`，等于主动阉掉推理 | `[ai] thinking = true`（`max_tokens` 自动抬到 4096） |
| 输入信息 | 题干里的图片被 `decode.py` 转成 `<img src="...">` 纯文本，模型看到的是一串 URL | 检测到图片就标记 `needs_review`，收尾汇总提示人工复核 |
| 提交方式 | 网页版能反复改，程序一次成型；多选「凑数」提示词会诱导多选 | 删掉凑数要求，改为 analysis 先推理再作答 |

键包含题型、题干、选项，三者任一不同就算不同题。落盘到 `ai_cache.json`，`_dirty >= 10` 时批量写入。

> ⚠️ 这里有个**真实踩过的坑**：`AICache` 定义了 `__len__`，导致空缓存在布尔判断里是 `False`：
>
> ```python
> if self._cache:        # 空缓存 → False → 缓存永远不生效
> ```
>
> 结果就是同一道题反复请求、反复花钱。改成 `if self._cache is not None:` 才对。
>
> **写自定义容器类时，不要随便实现 `__len__`** —— 它会悄悄改变对象的真假值语义。

**重试**：

```python
for attempt in range(1, max_retries + 1):
    try:
        completion = client.chat.completions.create(**kwargs)
    except Exception as exc:
        if self._is_fatal(exc):      # 401/402/403 重试没意义
            raise
    if attempt < max_retries:
        time.sleep(min(8.0, 1.5 ** attempt))    # 指数退避, 上限 8 秒
```

`_is_fatal()` 判断的是「重试也不会变好」的错误：Key 无效（401）、余额不足（402）、禁止访问（403）。这类错误直接抛，不浪费时间。429（限流）和 5xx 才退避重试。

**并发**：`solve_many()` 用 `ThreadPoolExecutor(concurrency)`，默认 4。上限 16，因为再高就容易撞 429。

**用量统计**：

```python
self.requests / failures / repairs / cache_hits
self.prompt_tokens / completion_tokens
```

结束时打印，方便估算花了多少钱：

```
[AI] 本次用量: 请求 32 次, 失败 0 次, 纠错 2 次, 缓存命中 8 次, tokens 45210/3120
```

### 7.5 作业/考试链路

#### 列表解析：不写死选择器

超星的列表页 DOM 结构改过很多次，写死 `div.work-item > a` 这种选择器必然失效。所以换个思路：

```python
TASK_URL_MARKERS = {
    "work": ("dohomeworknew", "workid=", "work/list/work"),
    "exam": ("reversionteststartnew", "examid=", "exam-ans/exam/test"),
}
```

遍历页面**所有** `a/div/li/span`，把 `href` 和 `onclick` 里的 URL 全抠出来，只要地址里含特征串就认为是入口。

好处是**页面给什么参数就原样用什么**：

```
/mooc-ans/work/doHomeWorkNew?courseId=111&classId=222&workId=333&answerId=444&enc=abc&cpi=555&ut=s
                              ↑这些参数一个都不用猜
```

如果自己拼 URL，`enc`（加密串）、`answerId`（作答记录 ID）、`cpi` 这几个必须精确，猜错就是 403 或空页面。

状态判断也是关键字匹配，且**顺序很重要**：

```python
FINISHED_KEYWORDS   = ("已完成", "已提交", "已交", "已批阅", ...)
UNFINISHED_KEYWORDS = ("未交", "未提交", "未开始", "未完成", ...)
```

先判 `UNFINISHED`，因为「未完成」里也含「完成」两个字——顺序反了会把所有未完成的都当成已完成。

#### 提交地址：优先用页面的

```python
payload = build_submit_payload(questions, report)
ok = self._submit(session, task, html, payload, submit=submit)
```

`_submit()` 的逻辑：

```
答题页 <form action="...">   ← 优先
  └─ 拿不到 → FALLBACK_SUBMIT_URLS[kind]
       work: addStudentWorkNew
       exam: addExamTranExamNew / saveExamTranExamNew
```

作业和考试的提交接口**不一样**，而且考试还分「交卷」和「保存」两个。页面自己写的 `action` 是最准的，所以优先用它。

#### 考试的两个特殊处理

**① 考试优先**

```python
if self.config["exam_priority"] and any(t.kind == "exam" for t in pending):
    pending = sorted(pending, key=lambda item: 0 if item.kind == "exam" else 1)
```

`pending` 原本是「作业在前、考试在后」（因为收集时按这个顺序）。时间盒一到 `break`，后面所有考试全被跳过。

而现实是：**作业能补交，考试过了截止就是零分**。所以考试必须优先。

用 `sorted` 而不是把两个列表交换，是因为 `sorted` 是**稳定排序**——同类内部保持原顺序，不会打乱章节间的递进关系。

**② 开考保护**

```python
def _exam_start_blocked(self):
    threshold = self.config.get("exam_min_remaining") or 0
    remaining = runtime_budget.remaining
    if remaining is None:
        return ""
    if remaining < threshold * 60:
        return f"本次运行只剩 {remaining/60:.0f} 分钟, 低于开考门槛 {threshold:g} 分钟, 留给下次运行"
```

原因：**点掉「开始考试」那一刻，超星的倒计时就开始走了**。如果随后被时长上限或 Actions 超时掐断，考试会停在「进行中」，而考试次数有限——这一次机会就废了。

宁可不开考，留给下次。

被推迟的考试计入 `stats.postponed`，**不算 skipped 也不算 failed**——它是「这次故意不做」，不是「做不了」或「做失败」。

## 8. 配置系统

### 8.1 三层优先级

```
命令行参数  >  配置文件 [节]  >  代码里的 DEFAULT
```

具体怎么落地，看 `init_config()`：

```python
if args.config:
    common_config, tiku_config, notification_config = load_config_from_file(args.config)
    ...
    answer_raw = dict(common_config.get("answer", {}))     # 复制一份, 不污染原配置
    if args.answer_submit:
        answer_raw["submit_policy"] = args.answer_submit   # 命令行覆盖
    common_config["answer"] = answer_raw
```

**为什么用 `dict(...)` 复制？** 因为要给「命令行覆盖」留一个干净的基线。直接改原字典的话，多次调用会互相污染（测试里尤其明显）。

### 8.2 归一化：字符串到类型

`configparser` 读出来的**一切都是字符串**。所以每个使用方都要自己归一化：

| 模块 | 函数 | 负责 |
| --- | --- | --- |
| `api/auto_answer.py` | `normalize_answer_config()` | `[answer]` 节 |
| `api/ai_solver.py` | `normalize_ai_config()` | `[ai]` 节 |
| `main.py` | `load_config_from_file()` | `[common]` `[tiku]` 节 |

统一风格是：**先取默认值，再逐项覆盖，非法值打警告然后回退**。

```python
def normalize_answer_config(raw, tiku_cover_rate=0.9):
    config = dict(DEFAULT_ANSWER_CONFIG)     # 先铺默认
    if not raw:
        return config                         # 没有就全用默认
    config["enable"] = as_bool(raw.get("enable"), config["enable"])
    ...
    try:
        config["exam_min_remaining"] = float(raw.get("exam_min_remaining", ...))
    except (TypeError, ValueError):
        logger.warning(...)
        config["exam_min_remaining"] = DEFAULT_ANSWER_CONFIG["exam_min_remaining"]
```

**绝不因为一个配置项写错就崩溃。** 用户把 `true` 写成 `ture`，正确的反应是「当 false 处理 + 告诉他」而不是抛异常。

### 8.3 布尔解析

INI 没有布尔类型，各家写法千奇百怪。统一的 `as_bool()`：

```python
str(value).strip().lower() in {"1", "true", "yes", "y", "on"}
```

`true` / `True` / `1` / `yes` / `on` 都算真，其余算假。

### 8.4 完整配置项清单

见 README 的 [配置文件详解](../README.md#配置文件详解)。这里只补充语义上容易误解的几项：

| 配置 | 容易误解的地方 |
| --- | --- |
| `[common] speed` | **不是可调项**。写 2 会打警告然后忽略，实际永远是 1 |
| `[common] jobs` | 只影响章节间并发。视频已经全局串行，调大只对文档/测验有加速作用 |
| `[tiku] submit` | **已废弃**。章节测验的提交改由 `[answer] submit_policy` 控制，这里只是兼容旧配置 |
| `[tiku] cover_rate` | 题库自己的覆盖率阈值；作业/考试/章节测验的提交阈值统一用 `[answer] min_cover_rate` |
| `[answer] order` | 作业与刷课的先后。默认 `before`，因为视频受时长上限约束，作业排最后会被饿死 |
| `[answer] exam` | 只控制**考试列表**，不影响章节测验 |
| `[answer] exam_min_remaining` | 只影响「要不要开始考」，不影响已经开考的 |

## 9. 二次开发指南

### 9.1 加一个题库 provider

**第 1 步**：在 `api/answer.py` 里写类，继承 `Tiku`：

```python
class TikuMyProvider(Tiku):
    def __init__(self):
        super().__init__()
        self.name = '我的题库'
        self._api = 'https://api.example.com/search'
        self._token = None

    def _init_tiku(self):
        # 从 self._conf 读 token 等配置, 只在启动时调用一次
        self._token = self._conf.get('tokens', '')
        if not self._token:
            logger.warning('我的题库缺少 tokens, 已停用')
            self.DISABLE = True

    def query(self, q_info):
        # 返回答案字符串, 没查到返回 None
        try:
            resp = requests.post(
                self._api,
                json={"question": q_info["title"], "options": q_info.get("options", "")},
                headers={"Authorization": f"Bearer {self._token}"},
                timeout=10,
            )
            data = resp.json()
            return data.get("answer") or None
        except Exception as exc:
            logger.warning(f'我的题库查询失败: {exc}')
            return None
```

**第 2 步**：注册：

```python
PROVIDER_REGISTRY = {
    ...
    'MyProvider': TikuMyProvider,
}
```

**第 3 步**：配置：

```ini
[tiku]
provider = MyProvider,TikuGo,DeepSeek
```

**约定**（不遵守会导致诡异行为）：

- `query()` 必须**吞掉异常返回 None**，不能往外抛。题库挂了不能拖垮整份作业。
- 返回的答案要**归一化**：判断题返回「正确/错误」，选择题返回字母或选项原文，多值用逗号分隔。
- `_init_tiku()` 里如果配置不全，设 `self.DISABLE = True` 而不是抛异常。

2. 在 `main.py::process_job()` 里加一个分支；
3. 在 `api/base.py` 里实现对应的 `study_xxx()` 方法，返回 `StudyResult`。

**关键约束**：新方法必须返回 `StudyResult`，并且**不要吞掉 `SKIPPED`/`FORBIDDEN` 语义**——调度器靠它判断要不要跳过、要不要重试。

## 10. 测试体系

### 10.1 为什么全部离线

八个测试文件，没有一个需要登录或真实网络：

| 文件 | 覆盖 | 用时 |
| --- | --- | --- |
| `test_auto_answer.py` | 列表解析、作答匹配、提交策略、考试开关、优先级、开考保护、端到端 | <1s |
| `test_ai_solver.py` | JSON 解析、字母纠错、缓存、重试、401 不重试、引擎联动 | <1s |
| `test_playback.py` | 倍速归一、闸门互斥、单位归一、真实速率、断点续播 | ~15s |
| `test_runtime_budget.py` | 上限解析、到点判定、队列清空、优雅停止 | ~10s |
| `test_study_work.py` | 章节测验门槛（题库/AI 任一可用）、提交策略、回滚强制提交 | <1s |
| `test_stuck_task.py` | 片尾不通过不死循环、无进展判定卡死、从头重播且只重播一次、正常视频不受影响 | ~15s |
| `test_chapter_order.py` | 章节内先内容后测验、到点后不再发起测验、已完成章节短路 | <1s |
| `test_video_quiz.py` | 弹窗题识别、普通卡片不误判、人脸采集识别、题目去重、initdata 解析、选项 name 映射、到点提交且只提交一次 | <1s |

**理由**：需要真实账号的测试等于没有测试。你不可能在 CI 里跑，也不可能在改代码后 30 秒内得到反馈。

### 10.2 怎么造假

**假 HTTP**：

```python
class FakeSession:
    def get(self, url, **kwargs):
        if "work/list" in url:
            return FakeResponse(WORK_LIST_HTML, url=url)
        ...
    def post(self, url, data=None, **kwargs):
        self.posted.append((url, data))          # 记录提交内容, 供断言
        return FakeResponse(payload={"status": True})
```

替换方式：

```python
original = SessionManager.get_session
SessionManager.get_session = classmethod(lambda cls: fake_session)
try:
    ...
finally:
    SessionManager.get_session = original       # 一定要还原
```

**假 AI 客户端**：

```python
class FakeCompletions:
    def create(self, **kwargs):
        self.calls.append(kwargs)
        return SimpleNamespace(choices=[...], usage=...)
```

然后注入：

```python
solver = AISolver(config, client=SimpleNamespace(chat=SimpleNamespace(completions=comp)))
```

`AISolver.__init__` 接受外部 client，就是为了这个——**依赖注入让测试不需要打桩库**。

### 10.3 需要真实等待的测试

`test_playback.py` 真的 `sleep` 4 秒、6 秒来验证「两个 3 秒的视频串行要 6 秒」。这是唯一能验证「节奏」的方法——mock 掉 `time.time()` 会把被测对象也一起 mock 掉。

断言留了余量：

```python
# 循环以 1 秒为粒度推进, 播完还要等下一轮才上报, 所以会多 1~2 秒
assert duration - 0.5 <= elapsed <= duration + 3.5
```

**不要把这些断言改成精确相等**，否则在慢一点的 CI 上必然挂。

### 10.4 加新测试的原则

1. **断言错误信息里带实际值**：`assert stats.answered == 2, f"应作答 2 份, 实际 {stats.answered}"` —— 挂了不用调试就能看出问题。
2. **测试要能独立跑**：每个 `test_xxx()` 自己准备数据、自己清理。
3. **全局状态必须还原**：`SessionManager`、`runtime_budget`、`playback_gate` 都是单例，改完要在 `finally` 里还原。

## 11. 设计取舍与已知限制

### 11.1 刻意的取舍

| 决定 | 代价 | 为什么值得 |
| --- | --- | --- |
| 视频 1 倍速 + 串行 | 40 小时课要跑 40 小时 | 唯一能通过时长校验的方式 |
| 章节测验排队 | 多测验章节慢几十秒 | 并发提交容易触发风控 |
| 时间盒是软上限 | 可能超出上限一个任务 | 硬掐断会留半截进度 |
| `SKIPPED` 不重试 | 本次不做的章节要等下次 | 重试无意义且会刷屏 |
| 考试剩余时间不足就不开考 | 可能少考一次 | 开考后被掐断会浪费一次机会 |
| 列表解析靠关键字 | 可能误抓无关链接 | 比写死 CSS 选择器存活久得多 |

### 11.2 已知限制

| 限制 | 说明 | 可能的解法 |
| --- | --- | --- |
| 人脸识别课程 | `videoFaceCaptureEnc` 只是透传，不做实际验证 | 需人工介入 |
| 考试提交偶发失败 | 部分考试用 JS 动态提交，`<form action>` 抓不到 | 靠兜底接口 + 手动交卷 |
| 验证码 | 出现图形验证码时只能跳过 | 需 OCR 或人工 |
| 直播任务 | `process_job` 里起线程后立刻 `join()`，实际是串行 | 可改真并发，但要单独限流 |
| `show_progress()` | 已无人调用，属于死代码 | 可删，保留是为兼容旧调用 |
| 缓存不区分课程 | 不同课程同一道题共用一个答案 | 通常无害，极少数会串 |

### 11.3 一个容易误解的点

「1 倍速 + 串行」听起来像限速，其实不是：

- **限速**是「让请求变慢」；
- **这里是让并发变成排队**。

区别在于：限速会让每个任务都变慢，而排队只是改变执行顺序，总工作量不变，总耗时从 `总和 / N` 变成 `总和`。后者才是真实的学习耗时。

## 12. 调试手册

### 12.1 日志级别

```bash
python main.py -c config.ini -v      # DEBUG, 会打印请求参数和响应片段
```

默认 INFO。DEBUG 会让日志量涨 10 倍以上，只在排查时开。

### 12.2 三个调试开关

| 开关 | 产出 | 用来看 |
| --- | --- | --- |
| `-v` / `--verbose` | DEBUG 日志 | 请求参数、解析中间结果 |
| `--answer-debug` | `answer_debug/*.html` | 作业/考试页面真实结构 |
| `[ai] check_connection` | 启动时一次连通性检查 | Key 是否有效 |

`answer_debug/` 有个贴心设计：**列表页一条都没解析出来时，即使没开 debug 也会自动存一份**。因为那种情况你根本不知道要开 debug。

### 12.3 常见症状 → 原因

| 症状 | 最可能的原因 | 怎么确认 |
| --- | --- | --- |
| 视频几秒就「播完」 | `playTime` 单位被当成秒 | 看日志里「视频时长 vs 本次实际耗时」 |
| 视频耗时远小于总时长 | 有并发没被闸门拦住 | 看日志有没有「排队等待」 |
| 任务点显示完成但后台没时长 | 之前用过倍速，被判定异常 | 只能重刷 |
| 403 反复出现 | 限流太激进 / 账号被临时限制 | 停几小时再试 |
| `没能从页面解析出题目` | 页面改版 | 看 `answer_debug/` 里的 HTML |
| `提交返回异常` | 提交接口变了 | 同上，去网页端手动交 |
| AI 一直报 429 | 并发太高 | 降 `concurrency` 到 2 |
| AI 报 401 | Key 错 / 多了空格 | 重新生成 |

### 12.4 定位「时间不对」的标准流程

这是最常被问到的问题，按顺序看三处日志：

```
① 任务完成: 第一章 视频 | 视频时长 12:30 | 起始进度 6:00 | 本次实际耗时 6:30
                                    ↑ 总长         ↑ 已看过       ↑ 本次耗时
   本次耗时 ≈ 总长 - 起始进度 → 正常

② 课程 高等数学 处理结束 | 累计播放 96.5 分钟, 排队等待 0.0 分钟
                            ↑ 真实播放总时长       ↑ 排队耗时(不应该太大)

③ 本次运行 91.5 分钟 / 上限 90 分钟 (已到上限)
```

如果 ① 的「实际耗时」明显小于「总长 − 起始进度」，程序会额外给一条 WARNING——那说明是**服务端提前放行**，不是本地的问题。

## 13. 术语表

| 术语 | 含义 |
| --- | --- |
| **任务点** | 章节里的最小学习单元，视频/文档/测验/阅读/直播各算一个 |
| **章节 (point)** | 课程目录里的一节，包含若干任务点 |
| **`cpi`** | 课程与班级的复合标识，很多接口要带 |
| **`dtoken`** | 视频播放的临时令牌，会过期，403 常因它失效 |
| **`enc`** | 进度上报的 MD5 签名，见 [3.4](#34-视频进度上报enc-签名) |
| **`isdrag`** | 是否拖动的标记，3=正常播放，4=拖动定位 |
| **`pyFlag`** | 测验提交开关，`""`=提交，`"1"`=只保存 |
| **播放位** | 全局单例信号量，保证同时只有一个视频在推进 |
| **作答位** | 全局单例信号量，保证同时只有一份测验在作答/提交 |
| **时间盒** | 单次运行时长上限，到点不接新活 |
| **软上限** | 只在不打断当前任务的前提下生效 |
| **覆盖率** | (题库命中 + AI 作答) / 总题数，决定要不要提交 |
| **`SKIPPED`** | 「这次故意没做」，不等于失败，不触发重试 |
| **`postponed`** | 考试因剩余时间不足推迟到下次 |
